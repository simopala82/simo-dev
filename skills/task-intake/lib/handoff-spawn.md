**spawn_task fields:**

- `title`: `Implement <jira-key-or-short-desc>` (≤60 chars, imperative)
- `tldr`: `Execute the implementation plan for <task gist> in an isolated session (context isolation).`
- `cwd`: the **repo root absolute path** — never omit it and never a subdirectory. This still matters even though the collision it originally guarded against can no longer happen: the pre-gate eligibility check (`SKILL.md` step 7.5) already routes an orchestrator whose own row is 3 straight to In-session, so a `spawn_task` hand-off is never built from inside an already-adopted worktree in the first place — there is no scenario left where omitting `cwd` could collide with the orchestrator's own tree. Pin it anyway: an omitted `cwd` still inherits this session's own cwd by default, an unpredictable value this file has no business relying on.
- **Corrected contract.** This bullet used to document a structural dead end: `spawn_task` always derives a fresh worktree from `cwd`, and `task-intake` used to run step 6 (worktree creation) before ever reaching this point — so the fresh worktree was always disconnected from whatever was already prepared, which went to waste (observed on `refactor/mr-review-tracker-scope-fetch`, MR !181: the tool's own result text said "start it in a fresh worktree with one click"). The fix defers step 6 past this point entirely — so the corrected contract is: the harness always places the spawned session inside its own fresh worktree under the given `cwd` — from the child's perspective this is always step 6's row 3, never row 1, regardless of what `cwd` was. The child must run `task-intake` step 3's pre-flight **itself**, from its own actual location — the orchestrator's own step 3 values describe a different filesystem location and must NOT be passed. This hand-off is offered only for a brand-new branch (row 3's adopt-rename step has no working path onto an existing one) — the orchestrator checks this before ever building the prompt.
- `prompt`: self-contained handoff — include all of:
  - a marker line as the prompt's opening line, rendered in the session/user language (same rule as `spawn-task/SKILL.md`'s prompt bullet: "the language of the current session/user, never a fixed language" — the other instruction bullets below are themselves quoted in English as literal instruction text, which is a different thing from the marker line's own language). English reference form: `[SPAWNED TASK — you are the session created specifically for what follows. This is not a live report; do not call spawn_task again for this same content.]`
  - the plan file's path *inside the worktree the child is about to create*: `<REAL>/.worktrees/<name>/docs/plans/...` on both row 1 and row 2 (step 6's own table uses `<REAL>` for both destinations — never `<TOP>`, which on row 2 is only the carry commit's *source*, not the destination) — not a path that exists yet when this prompt is written. On row 1/2, the base checkout's own copy was already carried away by the orchestrator's carry commit and no longer exists there by the time the child starts; on row 3/4 this hand-off is never reached (the pre-gate eligibility check routes those to In-session instead), so this bullet's "carried away" premise always holds for a spawn_task prompt that actually gets built. The `<worktree-abs>` used in the worktree-discipline instruction below is this same path, once the child has actually created it — not supplied ready-made.
  - branch name (pre-decided by the orchestrator — the child must NOT re-derive ticket/type/slug logic, just use this exact name; this is always a NEW branch, never a follow-up — the orchestrator only reaches this path on that condition)
  - `<base>` (the target branch step 6 branches from / fetches)
  - on row 1/2 only: `<carry-sha>` — the child cherry-picks this into its own worktree once created (`lib/worktree-carry.md`'s `cherry-pick -n`/`reset --quiet` steps, right where that file's own phase-marker comment says to resume), never before.
  - ticket key (if any) and 1-line task gist
  - explicit instruction: "Worktree discipline: use `git -C \"<worktree-abs>\"` for every git op and absolute worktree paths for scripts/tests. Do NOT assume the Bash cwd is the worktree and do NOT `cd` to establish context — the Bash cwd is unreliable in both directions (it can survive several calls, and can be silently re-anchored)."
  - explicit instruction: "Run task-intake step 3's pre-flight yourself, from your own actual location — do not assume you're in a plain repo root, and do not skip this step. Then run step 6's own procedure (unchanged) using the branch name and <base> above — whatever row your own step 3 resolves to, follow it exactly as documented. If a <carry-sha> was supplied, cherry-pick it into the worktree you just created once step 6 finishes. Only then proceed to plan-execute."
  - explicit instruction: "Read the plan, then proceed via `simo-dev:plan-execute`. Do NOT re-run intake steps 1-5, 7, or 7.5, and do NOT re-run grilling — the plan is final (user already approved it via the plan review gate)."
  - explicit instruction: "Default to `simo-dev:tdd` for feature/fix work. Skip TDD only if the plan explicitly says so."
  - explicit instruction: "If any test goes red unexpectedly, switch to `simo-dev:debug` before touching code."
  - explicit instruction: "When implementation is complete, run `simo-dev:review-loop` (gates on `simo-dev:verify-done`, so make sure tests/build are green locally first)."
