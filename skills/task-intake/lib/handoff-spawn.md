**start_session fields:**

- `initiation`: `user_asked` when reached via the `spawn` routing (the user answered `y` to "hand off to a fresh session" at step 7.5); `offer` when reached via `table-pick`'s silent pick (the user asked for the task, not for a separate session — `offer` is called with `title` alone, as the only tool call in its message, before any carry commit is built; it shows a "New session" / "Do it here" card and waits. Do it here → the In-session worktree row. New session → build the carry (row 1/2), then call again with `proposal_id`, `prompt` and `background` only (plus whatever the tool result asks for) — `cwd`, `use_worktree` and `source_branch` are not passed on this path, so the child may start in this checkout (row 1), which its own step 6 handles. `<REAL>` not this session's project → no `offer` at all (`SKILL.md` step 8 routes it in-session).)
- `source_branch` (with `use_worktree` `true`): `<base>`, only when it exists as a local branch in `<REAL>` (`git -C "<REAL>" rev-parse --verify --quiet "refs/heads/<base>"`; `start_session` takes an existing local branch only), else omit it — omitted, the app cuts the worktree from its own default (this session's base branch, else the repository's default branch), which on a repo whose `<base>` is not the default stops step 6's foreign-commit check.
- `context`: `fresh`; `use_worktree`: `true` — omitted from a plain checkout, the child would share this checkout's folder instead of getting its own desktop-app worktree (row 3a from its side). A child starting in the main checkout was also observed under the retired `spawn_task` (2026-10-01), cause not measured.

- `title`: with a ticket key, the `<KEY> <summary>` title built by `SKILL.md` step 5.6's **Rename session** rule (built even when that rename was skipped; the shared title is intended: this session can be archived after the spawn); without one, `Implement <short-desc>` (under 60 chars, imperative)
- `background` (required with `fresh`, ≥80 chars): `Execute the approved implementation plan for <task gist> in an isolated session (context isolation); intake and plan review already ran in the parent session.`
- `cwd`: the **repo root absolute path**, never a subdirectory — only when it differs from this session's project (`start_session` takes `cwd` for another folder only, and only with `user_asked`); same project → omit it, and the child is rooted at this project (its own worktree with `use_worktree` `true`). From a main checkout only — a submodule never hands off here (`SKILL.md` step 7.5's pre-gate condition 3). Omitting it for the same project starts the child from the project root the app knows, not from this session's Bash cwd.
- **Corrected contract.** This bullet used to document a structural dead end: the retired `spawn_task` tool always derived a fresh worktree from `cwd`, and `task-intake` used to run step 6 (worktree creation) before ever reaching this point — so the fresh worktree was always disconnected from whatever was already prepared, which went to waste (observed on `refactor/mr-review-tracker-scope-fetch`, MR !181: the tool's own result text said "start it in a fresh worktree with one click"). The fix defers step 6 past this point entirely — so the corrected contract is: with `use_worktree` `true` the app places the child inside its own fresh worktree of this project — from the child's perspective step 6's row 3. Not guaranteed: a child has also started in the main checkout itself (row 1, observed 2026-10-01 under `spawn_task`). A supplied `<carry-sha>` is applied on whatever row the child continues on. The child must run `task-intake` step 3's pre-flight **itself**, from its own actual location — the orchestrator's own step 3 values describe a different filesystem location and must NOT be passed. This hand-off is offered only for a brand-new branch (row 3's adopt-rename step has no working path onto an existing one) — the orchestrator checks this before ever building the prompt.
- `prompt`: self-contained handoff — include all of:
  - a marker line as the prompt's opening line, rendered in the session/user language (same rule as `spawn-task/SKILL.md`'s prompt bullet: "the language of the current session/user, never a fixed language" — the other instruction bullets below are themselves quoted in English as literal instruction text, which is a different thing from the marker line's own language). English reference form: `[SPAWNED TASK — you are the session created specifically for what follows. This is not a live report; do not call start_session again for this same content.]`
  - the plan file's path, **repo-relative** (`docs/plans/...`), with the instruction to resolve it against the child's own `<WT>` once its step 6 has run — the orchestrator cannot know that path: a child the desktop app placed lands on row 3a and keeps its own `<TOP>`, any other lands on `.worktrees/<name>`. Never the orchestrator's `<TOP>`, which on row 2 is only the carry commit's *source*. On row 1/2, the base checkout's own copy was already carried away by the orchestrator's carry commit and no longer exists there by the time the child starts; on row 3/4 this hand-off is never reached (the pre-gate eligibility check routes those to In-session instead), so this bullet's "carried away" premise always holds for a start_session prompt that actually gets built. The `<worktree-abs>` used in the worktree-discipline instruction below is the child's own `<WT>`, once its step 6 has run — not supplied ready-made.
  - branch name (pre-decided by the orchestrator — the child must NOT re-derive ticket/type/slug logic, just use this exact name; this is always a NEW branch, never a follow-up — the orchestrator only reaches this path on that condition)
  - `<base>` (the target branch step 6 branches from / fetches)
  - on row 1/2 only: `<carry-sha>` — the child cherry-picks this into the worktree step 6 leaves it in (`lib/worktree-carry.md`'s `cherry-pick -n`/`reset --quiet` steps, right where that file's own phase-marker comment says to resume), never before.
  - ticket key (if any) with its step-5.6 `<KEY> <summary>` title, and 1-line task gist
  - when a ticket key exists: explicit instruction: "Re-run step 5.6's own commands (`task-intake` `SKILL.md` step 5.6) for <KEY> now, its **Rename session** paragraph included, with the title given above (the spawn `title` is not guaranteed to become this session's title). Step 5.6 already ran in the parent session, best-effort (a failure there only prints a WARNING or a BLOCKED report, easy to miss in a long session) — re-running is safe: it never unblocks a Blocked ticket (that one reports BLOCKED again, rc 8), and is otherwise a no-op once the ticket is already assigned/at-or-past target, per step 5.6's own text; the rename is best-effort and never blocks."
  - explicit instruction: "Worktree discipline: use `git -C \"<worktree-abs>\"` for every git op and absolute worktree paths for scripts/tests. Do NOT assume the Bash cwd is the worktree and do NOT `cd` to establish context — the Bash cwd is unreliable in both directions (it can survive several calls, and can be silently re-anchored)."
  - explicit instruction: "Run task-intake step 3's pre-flight yourself, from your own actual location — do not assume you're in a plain repo root, and do not skip this step. Then run step 6's own procedure (unchanged) using the branch name and <base> above — whatever row your own step 3 resolves to, follow it exactly as documented. If a <carry-sha> was supplied, cherry-pick it into the worktree step 6 leaves you in, once it finishes. Only then proceed to plan-execute."
  - explicit instruction: "Read the plan, then proceed via `simo-dev:plan-execute`. Do NOT re-run intake steps 1-5, 7, or 7.5, and do NOT re-run grilling — the plan is final (user already approved it via the plan review gate)."
  - explicit instruction: "Default to `simo-dev:tdd` for feature/fix work. Skip TDD only if the plan explicitly says so."
  - explicit instruction: "If any test goes red unexpectedly, switch to `simo-dev:debug` before touching code."
  - explicit instruction: "When implementation is complete, run `simo-dev:review-loop` (gates on `simo-dev:verify-done`, so make sure tests/build are green locally first)."
