# `agent-dispatch` — delegated execution, batch-by-batch

Loaded on demand from `plan-execute` `SKILL.md` step 1 when `plan_execute_preflight.py` prints `execution: agent-dispatch?`, and from `lib/executor-dispatch.md`, which borrows items 1 and 3's ledger rules. `$MODEL` = the preflight's `model:` value, empty when it printed `inherit caller's tier`.

## Decide: `agent-dispatch` or `subagent`

`agent-dispatch` when both hold, else `subagent` (`lib/executor-dispatch.md`):
- no size-≥2 batch has a `Consumes:`/`Produces:` link between its own tasks' `**Interfaces:**` sections — the batching reflects only `**Files:**` overlap (mechanism: item 1's "Known, unmitigated limitation" below), so a link means that batch is wrong for parallel delegation: run `subagent`, never a plan edit;
- the batched tasks are substantial (more than a few edits each).

Print `SKILL.md` step 1's `Execution:` line with the mode decided here.

## Execution

Replaces `SKILL.md` step 2's direct execution; its ledger blocks and base-freshness checkpoint are the ones used below, and step 3's Report still follows. Batches execute in the order the preflight's `batches:` line printed them (`|` separates batches). For each batch:

1. Dispatch one `Agent` call per task in the batch — a single call for a size-1 batch, one call per task sent together in the same message for a size-≥2 batch, so they run concurrently. Every dispatch is `run_in_background: false` (never the `Agent` tool's own default of background): item 4 below needs every dispatch in the batch to have already returned before the checkpoint runs, which is exactly the "the very next action depends on this agent's result" case that calls for foreground — a batch of foreground calls sent together in one message all return together, before this step continues, with no separate wait-for-notifications step needed. Each dispatch's prompt carries: an ownership line (the agent owns that task's outcome within its declared Files, not just the listed edits); that task's own steps, read fresh from the plan file on disk; the worktree's absolute path, with the standing `git -C "<worktree-abs>"` discipline; that task's verification steps; the same "don't reorder steps without reason, capture surprising discoveries inline (CONTEXT.md / ADR / reference file), don't batch" discipline as `SKILL.md` step 2's direct execution; the plan-fidelity note from `SKILL.md` step 1 verbatim, plus the recorded spec path if one exists, with an explicit instruction to read that spec before trimming any plan snippet as out-of-scope rather than relying on the task's own `Files:`/`Interfaces:` lines alone; the line "Write throwaway files only under a fresh `mktemp -d /tmp/claude_<slug>.XXXXXX` of your own; never write into or overwrite files in the Scratchpad directory your environment lists — it belongs to the caller's session." verbatim; and an explicit instruction never to commit (task-level commits do not happen in this skill regardless of delegation — `simo-dev:commit` is the only place a commit is made) and to scope every git/file operation it performs to that task's own declared Files: paths only, never touching another task's files in the same batch — an In-scope improvement included, limited to that task's own declared `Files:`; the task's `### Task N:` title; and the absolute path of this plugin's `docs/canonical-flow.md` (never a worktree-relative one: plan-execute runs in any repo), resolved once with:
   ```bash
   R="${CLAUDE_PLUGIN_ROOT}"; [ -d "$R" ] || R="$HOME/.claude/local-marketplace/simo-dev"; [ -d "$R" ] || R="$(find -H "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/plugins/cache" -mindepth 3 -maxdepth 3 -type d 2>/dev/null | grep "/simo-dev/[^/]*$" | sort -V | tail -1)"
   echo "$R/docs/canonical-flow.md"
   ```
   Unless `<ledger-base>` is empty or the branch is protected, the prompt also carries the ledger paragraph's branch-point check block (`SKILL.md` step 2) with `<worktree-abs>` and `<ledger-base>` already substituted (the agent never sees this skill), and tells the agent to read that file's "In-scope improvements" (targets, and the "completes the branch's own change" exclusion) before its first check, then run the block before each improvement edit, target files in the ledger `file` path form. The agent names every In-scope improvement it made in its `✓ completed:` line (file — what — why, `file` relative to the repo root as `git status --porcelain` prints it) with at most one tag: its verdict (`pre-existing` / `branch-added` / `error`); `completes-branch` for one that completes the branch's own change, overriding any verdict, `pre-existing` included; or `exempt` for the improvement a task titled `In-scope improvement — …` is named after, which gets no check. With no check block in the prompt only `exempt` and `completes-branch` apply, and any other improvement carries no tag. The orchestrator appends the qualifying ones to the Also-fixed ledger (item 3; any other path form rewritten to the porcelain one before `add`). Known, unmitigated limitation: file-disjointness does not isolate *other* shared worktree/runner state — two dispatches in the same batch both running a whole-suite verification command (e.g. the full `pytest` suite) can race on a shared cache directory or a `.git` lockfile even though their own file sets never overlap, and the branch-point check's `git diff` touches `.git/index` too. Such a collision is indistinguishable from a genuine `⚠ blocked` outcome and is handled the same way (stop, surface, resume in-session) — no separate mechanism exists for it. `detect_independent_task_groups.py` has the same blind spot toward a task's `**Interfaces:**` block: two tasks whose `**Files:**` blocks don't overlap can land in the same batch even when one task's plan text `Consumes:` a name the other's `Produces:` line promises — see the decision above for the cross-check this implies. Model: pass `model: $MODEL` when non-empty, omit `model` entirely when empty (natural inherit-caller's-tier).
2. Each dispatch's final message must end with exactly one of:
   - `✓ completed: <summary + verification result + In-scope improvements made, each with its item-1 tag, if any>`
   - `⚠ blocked: <what's missing, what was tried>`
3. Mark every `✓ completed` task's todo completed, and append to the ledger (`SKILL.md` step 2's `add` block) exactly the In-scope improvements it tagged `pre-existing` or `exempt`. `branch-added`, `completes-branch`, `error` and untagged ones are not appended; untagged counts as `error`, and with `<ledger-base>` empty so does every non-`exempt` one. On a protected branch nothing is appended and nothing counts as `error`. `exempt` holds only when the text after `### Task N: ` in the title the orchestrator dispatched starts with `In-scope improvement — ` (the titular improvement may span several ledger lines, one per file); any other `exempt` counts as `error`. A batch containing a `⚠ blocked` task does not fail its siblings — their own `✓ completed` outcomes stand; only the blocked task's todo stays open.
4. Run `SKILL.md` step 2's base-freshness checkpoint (same block, unchanged, and rc table) **once for the whole batch**, after every dispatch in it has returned — not once per task within the batch (nothing in the checkpoint is task-specific, and running it concurrently per task would race the same worktree's git state for no benefit).
5. Any `⚠ blocked` outcome in the batch → stop here, surface it to the user exactly like `SKILL.md` "Hard stops" (the dispatch itself already refused to guess past it) — no task-level commits happened, so the worktree holds every completed task's work plus the blocked task's partial state, resumable in-session. Do not proceed to the next batch until resolved.
6. All tasks in the batch completed → continue to the next batch.
