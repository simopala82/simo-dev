# Canonical task flow

The default end-to-end flow for a ticket-driven task. Each step is a skill in `.claude/local-marketplace/simo-dev/skills/`.

## Steps

1. `simo-dev:task-intake <TICKET-KEY-OR-PROMPT>` — accepts a ticket key OR a free-text prompt. Runs high-level system-impact analysis (parallel Explore subagents on Sonnet), then opens the **Direction confirmation gate** (always-on): user can `y` / `redirect` / `deep-dive`. On `deep-dive`, escalates to `simo-dev:grill-me` (design mode for open scope, decisions mode for punctual decisions) per heuristic. Optionally creates a ticket (prompt mode), produces a detailed plan via `simo-dev:plan-write` (on the current checkout — no worktree yet), which runs its own plan-critique and **Plan review gate** before returning (exception: when step 4c's `Choices made:` list came back empty, `plan-write` itself is not invoked; the plan is written directly and the **Plan review gate** still runs against it, minus the plan-critique dispatch) — one gate with two shapes: `y`/`edit`/`restart` normally, or `y`/`n`/`edit`/`restart` when the hand-off signal fires, its `y`/`n` deciding in-session vs `start_session` (new branches only) — the worktree is still created only once hand-off executes, by whichever side executes. The hand-off signal fires when the plan is large (task count > 5, or file count > 8) or this task-intake run escalated to `grill-me` in design mode (not decisions mode) earlier in the same run, and either way only when `mcp__ccd_session__start_session` is callable, after the `ToolSearch` load described in "Deferred-tool availability" below — it never fires otherwise. Hand-off prompt to the implementation session carries the TDD-default and systematic-debugging-on-red discipline instructions. An umbrella split or a mid-flow late promotion redirects a branch's flow to a sub-task through a worktree-local, untracked `.claude/ticket-key-override` file, read before falling back to the branch-derived key, rather than by renaming an already-pushed branch, which would desync the branch name from any MR/PR already opened against it. `plan-write`'s plan-critique auto-applies objective findings to the plan file for up to 3 rounds before the gate above is shown; only judgment-level findings reach the human. Any uncommitted work this session already produced before hand-off — whether hand-off then keeps working in-session or spawns a fresh child — is carried across the worktree's creation or move as a throwaway carry commit, gated on which of a small set of pre-existing-worktree shapes this session's own tree matches rather than on whether the child is a spawned session or this same one; separately, adopting an already-existing harness-created worktree in place first parks (again a throwaway commit, never a `git stash`, since the stash is shared across every worktree of the repo) whatever pending work that tree already held, rebases the branch onto a fresh base, then restores the parked work. When hand-off does spawn a fresh child session, the child is not handed this session's own already-computed repo/worktree state — its own worktree lands somewhere this session cannot predict, so it re-runs its own repo pre-flight — and the parent passes it only the branch name, the base, and, when a carry commit was built here before spawning, that commit's SHA.
2. `simo-dev:plan-execute` — implement the plan in the worktree. Default mode: `simo-dev:tdd` for feature/fix work. On any unexpected red: switch to `simo-dev:debug` (hypothesis → isolate → verify → patch). Each task (or a small batch of them, per the executing gate's own batching) now runs as its own `Agent` dispatch instead of the whole plan executing inline in the main thread's own turn — see the `plan_execute` bullet under `## Model strategy` below for how that dispatch picks its model.
3. `simo-dev:review-loop` — gates on `simo-dev:verify-done` first (tests/build green, fresh evidence). Then auto-fix medium+ findings, plus `low` findings on diff files per "In-scope improvements", via `simo-dev:code-review-protocol`, with its validity filter applied to each finding BEFORE the fix (drops hallucinations / context-blind suggestions). Cap = `CAP`: 5, or a lower value the invoker passes for a prose-only diff (step 1.5); any surviving `high`/`critical` finding restores 5. Presents aggregated diff + rejected list before exit. After applying a round's passing fixes, a shared plan-drift check looks for any plan file under `docs/plans/` that declares a file the round just changed among its own target paths — a path-level check, not a content check; when a plan is flagged this way, the plan's text around that reference is read, and only if it still shows the pre-fix version of the code or text is the plan resynced with a targeted edit before the loop moves on to the next step, at no cost for a false-positive flag (the plan cites the file but the reviewed passage is unaffected), and with a plan-drift script failure logged but never blocking or aborting the round. Diff-capture gating applies at this step (both at review dispatch and at the final report), at `mr-followup`, and at `code-review-protocol`: a diff is captured through one shared script gated by size (roughly 50k characters), reading the full diff into context under the threshold and, over it, only `git diff --stat` plus per-file slices (for files under 1k lines) while the full diff is written to a temp file instead, to keep large diffs from bloating context — `mr-review` truncates its own diff at the same character threshold too, but via its own separate inline instruction, not this shared script. A clean ship-flow run cascades into `simo-dev:commit` (standalone review requests and headless runs stop at the report).
4. `simo-dev:commit` — step 0.7 runs the full three-question knowledge harvest first (`skills/commit/lib/knowledge-harvest.md`), then auto-runs `simo-dev:review-loop` unless a review already covers the pending files, harvest writes included (no ask; skips when no file changed after the last review), commits with conventional format scoped to the ticket, pushes (no gate on feature branches; a pre-push MR-state guard stops the push if the branch's MR was merged/closed mid-session — `lib/check_mr_state.py`; a guard that never answered stops first — the script is not there, or it printed nothing whatever it exited with — and only then the codes: exit 0 open / 1 terminal → stop / 2 unverifiable → stop / 3 absent → push), renders an informational mermaid preview, and creates the MR unconditionally (no gate). Protected branches keep their single commit+push confirmation gate instead (no MR).
5. `simo-dev:mr-followup` — after push, watches the pipeline, dispatches a local `simo-dev:code-reviewer` on the branch diff, and reads the MR/PR review comments. Applies the same `simo-dev:code-review-protocol` validity filter to medium+ findings, plus `low` findings on diff files per "In-scope improvements", BEFORE auto-fixing (remote comments come from reviewers without this session's context). Findings that pass the filter are fixed, committed, and re-pushed unconditionally (no gate; same MR-state guard before each re-push). Cap = `CAP`, same default, floor and escalation as review-loop (step 1.5); what the last permitted round *does* differs — here it surfaces without fixing. After applying a round's fixes and before that round's commit, it runs the same plan-drift check as step 3, but against the MR/PR's actual target branch rather than whatever `origin/HEAD` resolves to (the two can diverge), resyncing any stale plan file the same way. A clean-exit round runs a harvest catch-up pass against the same file before reporting, covering everything since `commit` step 0.7 (a step-1 review-loop included); a catch-up that writes something is committed as a fix round and re-reviewed by the next round (see below). Every stop before the merge that reports (clean exit, "Nothing to review", ambiguous, cap reached, a round-boundary stop) ends with the step 7.4 final report — MR/PR link, change, verifications, review summary, pipeline, skipped steps, next step — printed as chat text before any turn-closing call. Step 8 (post-merge) transitions the ticket to its configured `post_merge_state` (default `Ready for Testing`) — or, when the merged plan's header declares `**Deploy required:** no`, to its configured `post_merge_state_no_deploy` (default `Done`) instead — writes the "Verification notes" comment (consumed at release time by the release skill's per-ticket verify step), cleans up the worktree, and appends the dev-flow journal entry (step 8.5); then step 8.6 offers the next ready sibling sub-task as a new session (gated y/N), or the umbrella close once every sub-task is Done, both behind a user gate. Last, step 8.7 runs the repo's release hook, if configured (see "Configuring per-repo settings").

## Ticket auto-transitions

Forward-only, idempotent, opt-out, best-effort. The canonical flow walks the ticket through `In Progress` (intake) → `CodeReview` (post-push when MR exists) → a per-prefix `post_merge_state` (post-merge; defaults to `Ready for Testing` when unset) — or, when the merged plan declares `**Deploy required:** no`, `post_merge_state_no_deploy` instead (default `Done`). `Ready for Deploy` and `Done` happen at release time: the release skill's post-deploy per-ticket verify step (QA deploy → `Ready for Deploy`, prod deploy → `Done`), driven by the "Verification notes" comment mr-followup step 8 leaves on the ticket. Each transition looks up `transition_cmd` for the ticket's prefix (`lib/tracker_config.py`, `~/.claude/simo-dev/tracker.json`) and invokes it if configured; not configured (e.g. a read-only tracker) → the step is a no-op, no special-case in any skill body. Never moves the ticket backward. A `transition_cmd` failure — any non-zero exit, including a `--leaf-only` refusal on an **umbrella** (a key with sub-tasks) or a `--sync-parent` exit 7 (the umbrella's sub-tasks are all at/past Done — the close is a user-confirmed gate at post-merge, `simo-dev:mr-followup` step 8.6, or in a release skill mirroring the `next_subtask_cmd` contract) — only prints a warning (or, for intake's rc 8 below, a BLOCKED report); the flow always continues. Intake's `In Progress` call leaves a ticket flagged Blocked on the tracker side untouched (the binding exits 8, and `simo-dev:task-intake` step 5.6 reports it to the user); the post-push and post-merge calls pass `--clear-blocked`, which authorizes the binding to lift such a flag once the work is done. A binding with no Blocked concept accepts and ignores the flag. `--leaf-only` never advances the umbrella key directly; `--sync-parent` (added on every leaf transition) keeps it in sync with the aggregate of its sub-tasks instead — see `simo-dev:task-intake` step 2.5. Set `DEV_FLOW_NO_TRACKER=1` (or drop a `.claude/no-tracker` marker) to skip all transitions for the session.

## Configuring the tracker

Nothing above is JIRA-specific — `lib/tracker_config.py` maps a ticket-key prefix (`CUS`, `ACME`, whatever a project uses) to the commands and settings the flow uses for its tickets, listed below. Config lives at `~/.claude/simo-dev/tracker.json` (global per user, not versioned in this repo; override for tests only via `SIMO_DEV_TRACKER_CONFIG` or `--config`).

```bash
python3 lib/tracker_config.py get <PREFIX> <FIELD>
python3 lib/tracker_config.py set <PREFIX> <FIELD> <VALUE>
python3 lib/tracker_config.py run <PREFIX> <FIELD> [ARGS...]
python3 lib/tracker_config.py ticket-line <KEY>
```

Fields, one per prefix:

- `fetch_skill` — resolves a ticket's title/description/AC/status/links given its key (`task-intake` step 2).
- `transition_cmd` — invoked with the ticket key and a target state to move it forward (see above). It may also receive trailing flags (`--leaf-only`, `--sync-parent`, `--clear-blocked`) and must accept any it has no concept for. Exit code 8 is reserved for "ticket left untouched because it is Blocked on the tracker side" — `task-intake` step 5.6 reports any rc 8 as BLOCKED (see "Ticket auto-transitions" above).
- `create_skill` — creates a new ticket (`task-intake` step 5, `simo-dev:task-intake` step 2.5 for sub-tasks).
- `supports_subtasks` — `true`/`false`; gates automated sub-task creation for cross-repo/team work.
- `post_merge_state` — the state a ticket lands on post-merge; defaults to `Ready for Testing` when unset.
- `post_merge_state_no_deploy` — the state a ticket lands on post-merge instead of `post_merge_state`, when the merged plan's header declares `**Deploy required:** no`; defaults to `Done` when unset for the prefix.
- `next_subtask_cmd` — invoked as `<CMD> <leaf-key> [--resolved-at <state>]` after the post-merge transition; prints one JSON line with the leaf's umbrella, its next ready sibling sub-tasks, the pending ones with a reason, and whether every sub-task is Done. Sole consumer: `simo-dev:mr-followup` step 8.6. Empty stdout (or unconfigured) = no-op.
- `scope_fetch_cmd` — fetches ticket-view text for `lib/jira_scope.py`; `-` means explicitly declined, treated the same as unconfigured.
- `requirements_review_cmd` — writes a drafted Requirements/Acceptance Criteria block back to the ticket; invoked at `task-intake` step 4.5 (ticket mode) or step 5.5 (prompt mode).
- `comment_cmd` — invoked as `<CMD> <key> <body-file>`; posts the file as one ticket comment. Every gate comment the flow posts goes through it (`lib/post_tracker_comment.py`).
- `link_cmd` — invoked as `<CMD> <blocked-key> <blocker-key>`; records a "blocked by" link, already-linked counts as success (`task-intake` step 2.5).
- `assign_cmd` — invoked as `<CMD> <key>`; assigns the ticket to the current user, idempotent (`task-intake` step 5.6).
- `pr_body_ticket_line` — a template, not a command: `{key}` and `{number}` (the digits after the key's last dash) are substituted and the line is appended to the MR/PR body `simo-dev:commit` step 7 generates. Typical value for a tracker backed by the same repo's issues: `Closes #{number}`, so the forge closes the issue on merge. A key not ending in `-<digits>` gets no line. Preview with `ticket-line <KEY>`.

An unconfigured field is a silent no-op, never an error — a read-only tracker, or no tracker at all, both work out of the box. To disable tracker integration entirely for a repo or session: `DEV_FLOW_NO_TRACKER=1` or a `.claude/no-tracker` marker file.

Example — wiring `CUS` to an existing `jira-cli` wrapper (illustrative; any command that accepts the same arguments works):

```bash
python3 lib/tracker_config.py set CUS transition_cmd "jira-cli transition"
python3 lib/tracker_config.py set CUS post_merge_state "Ready for Testing"
python3 lib/tracker_config.py set CUS post_merge_state_no_deploy "Done"
```

## Configuring per-repo settings

Settings that belong to a repo rather than to a ticket prefix live in `~/.claude/simo-dev/repo.json` (global per user, not versioned; override for tests only via `SIMO_DEV_REPO_CONFIG` or `--config`), read and written by `lib/repo_config.py`. Entries are keyed by repo-id (`lib/repo_identity.py`): the normalized origin URL (`git.example.com/team/app`), or the main checkout's absolute path when there is no origin — the same value from every worktree of the repo. Not keyed by ticket prefix: one prefix often spans several repos that need different settings.

```bash
python3 lib/repo_config.py get --repo <any-checkout-or-worktree> <FIELD>
python3 lib/repo_config.py set <checkout-path-or-repo-id> <FIELD> <VALUE>
```

`set` accepts a checkout path or a literal repo-id / origin URL, so a repo can be configured without a local clone. Prefer the checkout path; a literal URL must be the one `git remote get-url origin` prints, since an ssh form with a port does not normalize to the same id as its https form. `get` prints the value, or nothing when unset, with rc 0 either way.

Fields, one per repo:

- `release_skill` — a skill name. Sole consumer: `simo-dev:mr-followup` step 8.7, which runs after every other post-merge step and invokes it with the Skill tool and args exactly `post-merge`; the skill owns its own gates and output from there. Unset = no output at all. It needs no ticket, and runs only after a user-confirmed merge. Invocation environment: the task worktree is normally removed by then and the Bash cwd may still point at that unlinked directory, and the main checkout may not have been refreshed. So the skill must not rely on its cwd: it resolves its repo by absolute path and fetches what it needs itself.

Example (illustrative):

```bash
python3 lib/repo_config.py set git.example.com/team/app release_skill my-plugin:my-release
```

## Proactive review-loop auto-run — runtime behavior

When implementation work concludes, the main thread auto-invokes `simo-dev:review-loop` and proceeds — no up-front ask — BEFORE the user asks to commit/push/merge. Catches issues earlier. It skips only when the loop is clearly not useful (trivial doc/typo edit, empty diff, or a review already covering the pending files). Inside a `simo-dev:mr-followup` run nothing the run does is a trigger; any other review-loop waits as "In-scope improvements" (Transparency) and `simo-dev:mr-followup` "No Also-fixed ledger work inside a run" describe. CLAUDE.md carries the eager trigger list — the linguistic phrases, the implementation triggers and the pre-commit/push/merge points — because it is the only surface that carries rule *bodies* on every turn (skill `description` fields are in the listing every turn too, and some do carry an imperative — `simo-dev:commit`'s says never to run `git commit` directly — but a description is budgeted in sentences, not in rule sets). `simo-dev:guide` restates the list for whoever loads that file; neither it nor this one loads by itself. The one mechanical backstop is `hooks/review_loop_warn.py`, self-gated to `git commit` alone. Two skip conditions are decided by code — "a review already covers the pending files" (`lib/review_marker.py` compares each pending file's mtime against the last review record) and "empty diff" (the hook exits silently on an empty candidate list); "trivial doc/typo edit" is the judgment call. The loop still gates on unresolved findings; a clean run hands off to `simo-dev:commit` directly (step-8 exceptions: standalone review request, headless run, commit pre-flight).

If review-loop runs clean, the next `simo-dev:commit` invocation will default the review-loop gate to skip (per the deterministic `lib/review_marker.py check` in `skills/commit/SKILL.md` step 1), unless step 0.7's harvest writes something, which step 1 then re-reviews. The record lives in `~/.claude/state/review-loop`, written by `hooks/review_record.py` when the code-reviewer subagent *concludes* (`SubagentStop`) — an observed event, not a claim, and deliberately not the `Agent` tool returning, which for a background dispatch is only the launch acknowledgement. The event is necessary and not sufficient: the hook also gates on the reviewer having concluded (a non-empty `last_assistant_message`, or, when the report went out through a `SubagentHandback` call and that field is absent, the transcript ending on that call; an interrupted subagent normally has neither, and one stopped while the handback itself runs already holds its full report), on a line-1 `REPO:` marker naming an existing git repo, and on a session id (read the hook for the full set). There is no TTL: a commit is covered when no file in it is newer than the last review.

## Model strategy

`lib/model_strategy.py` (get/set on `~/.claude/simo-dev/model-strategy.json`, four fixed categories) lets a user pick which model backs each of this plugin's own `Agent` dispatch points, independently of whatever model the session itself is running. `simo-dev:model-strategy` wraps it interactively — easier than the raw CLI shown below.

- Main thread: runs whatever model the session is configured with (e.g. via `/model`) — this plugin does not configure or auto-switch it. The categories below are this plugin's own dispatch points, not the session model.
- `explore_research`: `Explore`'s one dispatch site (`task-intake` step 3) reads `lib/model_strategy.py get explore_research`, defaulting to `sonnet` when unconfigured (today's behavior, unchanged) — no longer a hardcoded pin at that call site. `general-purpose` has no dispatch site anywhere in this plugin, so it stays pinned to `sonnet` in its own agent frontmatter (`~/.claude/agents/general-purpose.md`) with no config hook.
- `code_review`: `simo-dev:code-reviewer`'s three dispatch sites (`code-review-protocol`, `mr-followup` local review, `mr-review` step 5) each read `lib/model_strategy.py get code_review` before dispatch and pass `model:` only when non-empty — still no `model:` pin in `agents/code-reviewer.md` itself; an empty config reproduces today's inherit-the-caller's-tier behavior. Effort is a different lever: the `Agent` tool takes no per-dispatch effort, so `model_strategy` covers model only, and both reviewer agents (`code-reviewer`, `plan-reviewer`) pin `effort: high` in their own frontmatter and deny `Edit`/`Write`/`NotebookEdit` via `disallowedTools` (Bash stays). Two known limits of the pin: per the subagent docs it overrides the session's effort, so it would also lower a reviewer under an `xhigh`/`max` session (per docs, not measured); and its behavior when `model_strategy` points a reviewer at a model without effort support (e.g. Haiku 4.5) is untested. `Plan` (the built-in agent) has no dispatch site in this plugin, so it is unaffected and keeps inheriting the caller's tier with no config hook.
- `plan_critique` (skipped entirely for a bare plan — same condition as the **Plan review gate** exception above: step 4c's `Choices made:` list came back empty, so `plan-write` itself never runs): `simo-dev:plan-write`'s own review gate dispatches a new `simo-dev:plan-reviewer` agent after writing the plan, reading `lib/model_strategy.py get plan_critique` and defaulting to `sonnet` when unconfigured — a call-site default, same pattern as `explore_research`. Set it to `none` to disable automatic plan critique dispatch entirely. `plan-reviewer` carries the same `effort: high` pin and read-only tool denial as `code-reviewer` (see the `code_review` bullet, limits included).
- `plan_execute`: `simo-dev:plan-execute`'s own execution delegation gate (step 1) reads `lib/model_strategy.py get plan_execute` before each per-task/per-batch `Agent` dispatch and passes `model:` only when non-empty — same inherit-the-caller's-tier default as `code_review`, no `none` sentinel (that concept is `plan_critique`-specific).
- Background `Agent` calls (not `Bash`) doing mechanical work (log tail, doc generation, wide read-only scans) are not wired to any category above, and no script in this plugin dispatches one today — treat that as a documented intention for a future dispatch, not enforced behavior.
- Every subagent this plugin dispatches (`Explore`, `code-reviewer`, `plan-reviewer`, or any other `Agent`-tool child) must work in-line within its own turn and return its findings as its final message — never spawning its own `Agent` children, never using `run_in_background`. A subagent can't await its own background children, so the dispatching skill would get an empty punt instead of the results. It also inherits the caller's Scratchpad directory in its environment block, so a throwaway script it writes there can overwrite a same-named one of the caller's: `code-reviewer`/`plan-reviewer` carry a `mktemp -d` rule in their own definition, and the dispatch prompts of `task-intake` (step 3 `Explore`, step 8 parallel agents), `plan-execute` (delegated tasks), `commit` step 7 and `mr-review` (the `mr_presentation` agent, line appended at dispatch) carry it as a line. A new dispatch site needs the same line, and so does a reviewer dispatch overridden to a non-simo-dev agent type (e.g. `mr-review`'s `DEV_REVIEW_MR_AGENT_TYPE`), which loses the definition's rule. The `/tmp/claude_` prefix keeps the dir inside the usual `/tmp/claude_*` allow rules; a bare `mktemp -d` lands under `$TMPDIR`.

Example — opting `code_review` into a higher-tier model (illustrative; the config file does not exist until the first `set`, so nothing here changes behavior by default):

```bash
python3 lib/model_strategy.py set code_review opus
```

## Dev-flow journal & knowledge harvest

After each merged task, `simo-dev:mr-followup` step 8.5 appends one block to `~/.claude/state/dev-flow-journal.md`. Each entry records: `mode` (flow path: direct/grill-me, derived from the skill logger), ticket, task, model, effort, tokens, skills used, review-loop iterations, post-MR auto-fixes, pipeline-first-try, problems/friction, notes. `tokens`, `model` and `effort` are auto-derived: `model`/`effort` by `lib/session_meta.py` from the main transcript's last assistant turn (`unknown (<reason>)` when unavailable, a `(mixed: …)` suffix on a model switch). Limit: "last assistant turn" belongs to the session that runs step 8.5 — a resumed session, or one switched to a cheaper model before mr-followup, records that model rather than the one that implemented the task; `(mixed: …)` only covers a switch inside that same transcript. No A/B experiment framing — this is a personal operational log.

The knowledge harvest — a three-question session review routing durable facts to their home:
domain terms → `CONTEXT.md`, hard-to-reverse decisions → `docs/adr/`, gotchas/invariants →
`CLAUDE.md` or a reference file — runs pre-merge, not here. `commit` step 0.7 runs the primary,
full pass before every commit, ahead of its review pre-flight; `mr-followup` step 7's clean-exit
branch runs a lighter catch-up pass scoped to what emerged since `commit` step 0.7 (a step-1
review-loop included), and a catch-up that writes something is committed as a fix round and
re-reviewed by the next round. Both against
`skills/commit/lib/knowledge-harvest.md`. Existing homes, or a newly *approved* one (the
procedure asks once before creating `CONTEXT.md` / `docs/adr/` / a repo-specific file the first
time a repo lacks one) — never an invented one. Skip when nothing qualifies.

## In-scope improvements

An **In-scope improvement** is a change beyond the literal request that touches only files already in the current task's diff or plan.

- **Never spawn a follow-up for one** (`start_session` or otherwise): do it in the current task.
- Needs the user's decision (a reasonable alternative exists) or would swell the diff noticeably → ask in-session. Never spawn silently, never skip silently.
- A change reaching any file or repo outside the task stays a follow-up (existing spawn rules unchanged).
- **Pre-existing dead code** in a file in the diff: delete it when `rg -uu` over the repo finds no other use of the symbol (hits only in plans/specs under `docs/` or in build output are not uses — name them in the evidence); the evidence goes in the "Also fixed" entry. Not verifiable by search (reflection, runtime-built names, external entry points) → ask. Outside the diff → mention only.
- **Review findings**: `low` findings on files in the diff are applied while an iteration remains under `CAP`. This can cost up to the iterations remaining under `CAP` (each review may surface new `low`s), never more. On the last iteration they are listed only: editing after a clean exit invalidates the review record. An applied `low` is an In-scope improvement only when the **branch-point check** says so: `lib/branch_point_check.py`, run once per iteration/round, before any fix of it is applied, on every `low` that passed the validity filter, against the merge-base the calling skill's review diff used. Its targets are the cited `file:line` plus every line the fix will replace or remove, or, for a fix that only inserts, the lines on both sides of the insertion point. All `pre-existing` → In-scope improvement. Any `branch-added` → a fix of the branch's own work, which is part of the requested work, not beyond it: applied, not ledgered, not under "Also fixed". `error`, or no verdict (the call failed) → same as `branch-added`, and named in the skill's report. A `low` from a remote MR comment, or a `low`, `simo-dev:plan-execute` improvement or ad-hoc edit that completes the branch's own change (e.g. documents a flag the branch added, on a pre-existing line, or re-adds a line the branch removed), is never an In-scope improvement, whatever the check says.
- **Unattended runs never ask**: one needing a decision is skipped and reported as `deferred (needs decision)`.
- **Transparency**: each one is declared in one line (file, what, why) — in the commit message body of the first commit that carries it, and in the MR body's `### Also fixed` section when the MR is created. Once the MR exists (mr-followup rounds, later commits) the commit message is the record; the MR body is not rewritten. One known at plan time also gets its own plan task. Every one made through `simo-dev:commit` (plan-execute, review-loop, an ad-hoc edit in the flow; for review-loop an applied `low` only on an all-`pre-existing` branch-point check; for plan-execute or an ad-hoc edit, any improvement but the one a task titled `In-scope improvement — …` is named after (a plan-execute-only exemption) only on an all-`pre-existing` branch-point check run before the edit, whose targets are the lines the improvement will replace or remove, or both sides of a pure insertion, the first line alone at start of file and the last line alone at end of file, since neither, unlike a review finding, has a cited `file:line`) is recorded in the **Also-fixed ledger** as soon as it is made: `lib/also_fixed_ledger.py add`, always in the single call form of `simo-dev:review-loop` `### 6. ## Code review severity

Used by `simo-dev:review-loop` and `simo-dev:mr-followup`.

- `low` — style/cosmetic. On a file in the diff, applied per "In-scope improvements" (under `CAP`); otherwise informational.
- `medium` — code smell, missing test coverage, minor bug, perf concern. Auto-fixed.
- `high` — correctness bug, security issue, data-loss risk. Auto-fixed.
- `critical` — blocks merge. Auto-fixed; surfaced even if iteration cap is reached.

Reviewer subagent must emit findings as `[severity] file:line — message` (one per line).

## Deferred-tool availability

A tool can be callable, listed only as deferred, or absent in a given session. Every availability gate on a tool that can be deferred decides the same way:

- Already callable (including loaded earlier this session) → use it.
- Otherwise (listed only as deferred, or not listed at all) → run `ToolSearch` `select:<full-tool-name>` once. Never skip that load because the name is not listed.
- Schema returned → available. No schema (a denied or failed `ToolSearch` included), or no `ToolSearch` tool → not available: the site's own fallback, unchanged.

Tools gated this way (observed, not a closed set): `SendMessage`, `mcp__ccd_session__start_session`, `mcp__ccd_session__mark_chapter`, `mcp__visualize__show_widget`, the `mcp__ccd_session_mgmt__*` tools. Each site states the load inline and keeps its own fallback; none depends on this section being read.

Observed 2026-09-30: the visualize server can register only under a hashed `mcp__<uuid>__` prefix. `select:` on the canonical name then returns no schema and the site falls back — expected, not a regression.

## Local dev refresh

The `simo-local` marketplace is a directory source: the installed copy is cached at `~/.claude/plugins/cache/simo-local/simo-dev/<version>/` and `claude plugin update` is a **no-op unless `plugin.json` `version` is bumped**. After editing the plugin source in place, force a fresh cache with:

```bash
claude plugin uninstall simo-dev@simo-local && claude plugin install simo-dev@simo-local
```

(or bump `version` in `plugin.json`). Restart Claude Code / `/reload-plugins` to load the refreshed skills.
