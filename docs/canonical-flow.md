# Canonical task flow

The default end-to-end flow for a ticket-driven task. Each step is a skill in `.claude/local-marketplace/simo-dev/skills/`.

## Steps

**Activation.** The flow is dormant until `simo-dev:task-intake` runs. It writes two keys (`lib/flow_state.py`), and either one means active: a session flag under `~/.claude/state/dev-flow/active/` (step 1; it also carries the task ID of the flow events, "Dev-flow journal & knowledge harvest" below; pruned after 7 days with no positive check) and a marker in the worktree's own git dir (step 6, both keys again so a `start_session` child gets its own flag). `simo-dev:mr-followup`'s post-merge cleanup clears the marker; the session flag stays for the rest of the session, past the merge, so a later task there is still in the flow; `flow_state.py off` ends it by hand. The warning hooks (`base_freshness_warn.py`, `mr_followup_remind.py`) stay silent outside the flow (one exception: `mr_followup_remind.py`'s merge reminder, which fires whenever the session holds a task with no `outcome`), and a SessionStart hook (`flow_session_start.py`) prints one line when a session starts inside it. A UserPromptSubmit hook (`reuse_warn.py`) warns once when a session whose task ended (an `outcome`, or released with `handoff`) gets a prompt after more than an hour idle: new work is cheaper in a new session. It never blocks. Outside the flow the only traces are `reuse_warn.py` (below; it reads the task files, not the flow flag) and `review_loop_warn.py`'s one-line `simo-dev advisory: no review recorded`, on a commit or push of a non-protected branch with unreviewed files, once per session, repo, branch and event — never a block. `simo-dev:afk` refuses to run outside the flow; a standalone `simo-dev:grill-me` does not start it.

1. `simo-dev:task-intake <TICKET-KEY-OR-PROMPT>` — accepts a ticket key OR a free-text prompt. First, off the decided-brief path, a **resume check** (`skills/task-intake/lib/resume-path.md`, `lib/resume_point.py`) reads the checkout: work already in progress outside the flow re-enters it at the step it reached, behind one confirmation (`--adopt` skips it) — an open MR/PR with nothing new → `mr-followup`; a branch that adds a plan and only intake artifacts → `plan-execute`; any other work, or new local work on an open MR/PR → `review-loop` (or "continue implementing"); a protected branch with tracked changes or local commits, or a merged/closed MR/PR with local work left on it → stop (a merged/closed one with nothing local → a full intake). A resume runs only the repo pre-flight, the ticket steps (5, 5.6) and step 6, which adopts a main checkout, a canonical worktree, or a harness tree on a named non-`claude/*` branch in place (post-merge then leaves a main checkout and its branch alone, and a main checkout gets the session flag only, no marker), then invokes that step; its default letter is the resume when the arguments are empty or name the branch's own ticket, a full intake otherwise. Otherwise it runs high-level system-impact analysis (parallel Explore subagents on Sonnet), then opens the **Direction confirmation gate** (always-on, except on a decided brief, see "Decided brief" below): candidate directions, `deep-dive` and `redirect` as one lettered list with a single `Recommended:` line that `y` confirms. On `deep-dive`, escalates to `simo-dev:grill-me` (design mode for open scope, decisions mode for punctual decisions) per heuristic. Optionally creates a ticket (prompt mode), writes a plan brief (direction, `Choices made:`, requirements, analysis paths, grill-me outcome, the user's constraints in their own words) and dispatches the `simo-dev:plan-writer` subagent, which writes the plan (on the current checkout — no worktree yet) by `simo-dev:plan-write`'s rules and reports back; task-intake's **Plan review gate** dispatches the plan-critique rounds, sends their fixes and the user's gate edits back to the same writer (`SendMessage`), and builds its summary with `lib/plan_summary.py`, so the main session never reads the plan (exception: when step 4c's `Choices made:` list came back empty, no writer runs; the plan is written directly and the **Plan review gate** still runs against it, minus the plan-critique dispatch) — one lettered gate with a single `Recommended:` line that `y` confirms: `proceed` / `apply and proceed` / `apply and re-present` / `edit` / `restart`, plus a `proceed in a new session` option (new branches only, `start_session`) that is never recommended, since execution and review already run in subagents — the worktree is still created only once hand-off executes, by whichever side executes. Hand-off prompt to the implementation session carries the TDD-default and systematic-debugging-on-red discipline instructions. An umbrella split or a mid-flow late promotion redirects a branch's flow to a sub-task through a worktree-local, untracked `.claude/ticket-key-override` file, read before falling back to the branch-derived key, rather than by renaming an already-pushed branch, which would desync the branch name from any MR/PR already opened against it. The gate's plan-critique auto-applies every `→ fix:` finding, at any severity, to the plan file before the gate above is shown, for at most the plan header's `Critique rounds` (risk-scaled, first match wins: 3 for a declared risk, 1 only for small docs-only plans (skill, agent, command, hook and rule bodies count as code), else 2, and 2 when missing; gate re-entries count, an explicit `edit` always gets one more round, and the last round's fixes are applied without a new dispatch); only `→ decide:` findings reach the human, and the gate's apply options take their recommended options. Any uncommitted work this session already produced before hand-off — whether hand-off then keeps working in-session or spawns a fresh child — is carried across the worktree's creation or move as a throwaway carry commit, gated on which of a small set of pre-existing-worktree shapes this session's own tree matches rather than on whether the child is a spawned session or this same one; separately, adopting an already-existing harness-created worktree in place first parks (again a throwaway commit, never a `git stash`, since the stash is shared across every worktree of the repo) whatever pending work that tree already held, rebases the branch onto a fresh base, then restores the parked work. When hand-off does spawn a fresh child session, the child is not handed this session's own already-computed repo/worktree state — its own worktree lands somewhere this session cannot predict, so it re-runs its own repo pre-flight — and the parent passes it only the branch name, the base, and, when a carry commit was built here before spawning, that commit's SHA.
2. `simo-dev:plan-execute` — implement the plan in the worktree. Default mode: `simo-dev:tdd` for feature/fix work. On any unexpected red: switch to `simo-dev:debug` (hypothesis → isolate → verify → patch). Whether tasks run inline (a plan of 12 steps or less), in one clean-context executor subagent that returns a short report (the default above that size), or as `Agent` dispatches (one per task, a batch of file-disjoint, interface-independent, substantial tasks running together) is decided and announced by plan-execute's execution delegation gate, never asked — see the `plan_execute` bullet under `## Model strategy` below for how that dispatch picks its model.
3. `simo-dev:review-loop` — gates on `simo-dev:verify-done` first (tests/build green, fresh evidence). Then auto-fix medium+ findings, plus `low` findings on diff files per "In-scope improvements", via `simo-dev:code-review-protocol`, with its validity filter applied to each finding BEFORE the fix (drops hallucinations / context-blind suggestions); the filter and the fixes run in a clean-context fixer subagent, so only its report reaches the main session. Cap = `CAP`: 5, or a lower value the invoker passes for a prose-only diff (step 1.5); any surviving `high`/`critical` finding restores 5. Presents aggregated diff + rejected list before exit. After applying a round's passing fixes, a shared plan-drift check looks for any plan file under `docs/plans/` that declares a file the round just changed among its own target paths — a path-level check, not a content check; when a plan is flagged this way, the plan's text around that reference is read, and only if it still shows the pre-fix version of the code or text is the plan resynced with a targeted edit before the loop moves on to the next step, at no cost for a false-positive flag (the plan cites the file but the reviewed passage is unaffected), and with a plan-drift script failure logged but never blocking or aborting the round. Diff-capture gating applies at this step (both at review dispatch and at the final report), at `mr-followup`, and at `code-review-protocol`: a diff is captured through one shared script gated by size (roughly 50k characters), reading the full diff into context under the threshold and, over it, only `git diff --stat` plus per-file slices (for files under 1k lines) while the full diff is written to a temp file instead, to keep large diffs from bloating context — `mr-review` truncates its own diff at the same character threshold too, but via its own separate inline instruction, not this shared script. A clean ship-flow run cascades into `simo-dev:commit` (standalone review requests and headless runs stop at the report).
4. `simo-dev:commit` — step 0.7 runs the full three-question knowledge harvest first (`skills/commit/lib/knowledge-harvest.md`), then auto-runs `simo-dev:review-loop` unless a review already covers the pending files, harvest writes included (no ask; skips when no file changed after the last review), commits with conventional format scoped to the ticket, pushes (no gate on feature branches; a pre-push MR-state guard stops the push if the branch's MR was merged/closed mid-session — `lib/check_mr_state.py`; a guard that never answered stops first — the script is not there, or it printed nothing whatever it exited with — and only then the codes: exit 0 open / 1 terminal → stop / 2 unverifiable → stop / 3 absent → push), renders an informational mermaid preview, and creates the MR unconditionally (no gate), then posts the "Verification notes" comment on the ticket (consumed at release time). Protected branches keep their single commit+push confirmation gate instead (no MR). The MR/PR opens as Draft on `--draft` or when a plan the branch adds declares `**MR draft:** yes` in its header (`simo-dev:plan-write`); `--no-draft` forces a non-Draft one.
5. `simo-dev:mr-followup` — after push, watches the pipeline, dispatches a local `simo-dev:code-reviewer` on the branch diff (skipped on round 1 when this session's review-loop record still covers every branch file and left nothing unresolved), and reads the MR/PR review comments. Applies the same `simo-dev:code-review-protocol` validity filter to medium+ findings, plus `low` findings on diff files per "In-scope improvements", BEFORE auto-fixing (remote comments come from reviewers without this session's context). Findings that pass the filter are fixed, committed, and re-pushed unconditionally (no gate; same MR-state guard before each re-push). Cap = `CAP`, same default, floor and escalation as review-loop (step 1.5); what the last permitted round *does* differs — here it surfaces without fixing. After applying a round's fixes and before that round's commit, it runs the same plan-drift check as step 3, but against the MR/PR's actual target branch rather than whatever `origin/HEAD` resolves to (the two can diverge), resyncing any stale plan file the same way. A clean-exit round runs a harvest catch-up pass against the same file before reporting, covering everything since `commit` step 0.7 (a step-1 review-loop included); a catch-up that writes something is committed as a fix round and re-reviewed by the next round (see below). Every stop before the merge that reports (clean exit, "Nothing to review", ambiguous, cap reached, a round-boundary stop) ends with the step 7.4 final report — MR/PR link, change, verifications, review summary, pipeline, skipped steps, next step — printed as chat text before any turn-closing call. A repo whose own rules want a release or version-bump commit in the MR makes it after the clean exit, right before the merge, not at step 4: a fix round here would otherwise force a second release, and a committed bump costs the round-1 skip; the release push starts no new round. After a clean exit, step 7.6 prints a merge brief (task ID, MR, branch, worktree, ticket, QA gate) and, outside `simo-dev:afk`, a `start_session` card: the merge often waits past the one-hour prompt cache, and a fresh session started from the card (`simo-dev:mr-followup merge`) runs the merge gate and steps 8-8.7 from the brief alone, joining the task through the brief's `task id:` line and closing the parked session's hold. Replying `merge` in the parked session still works. Step 8 (post-merge) transitions the ticket to its configured `post_merge_state` (default `Ready for Testing`) — or, when the merged plan's header declares `**Deploy required:** no`, to its configured `post_merge_state_no_deploy` (default `Done`) instead — posts a "Verification notes" comment only when none was posted at MR open, or when the merged head or a passing step 7.5 changed the notes (the notes are kept current before every step 7.4 report by a supersede check), cleans up the worktree, and appends the dev-flow journal entry (step 8.5); then step 8.6 offers the next ready sibling sub-task as a new session (gated y/N), or the umbrella close once every sub-task is Done, both behind a user gate. Last, step 8.7 runs the repo's release hook, if configured (see "Configuring per-repo settings").

## Ticket auto-transitions

Forward-only, idempotent, opt-out, best-effort. The canonical flow walks the ticket through `In Progress` (intake) → `CodeReview` (post-push when MR exists) → a per-prefix `post_merge_state` (post-merge; defaults to `Ready for Testing` when unset) — or, when the merged plan declares `**Deploy required:** no`, `post_merge_state_no_deploy` instead (default `Done`). `Ready for Deploy` and `Done` happen at release time: the release skill's post-deploy per-ticket verify step (QA deploy → `Ready for Deploy`, prod deploy → `Done`), driven by the "Verification notes" comment `simo-dev:commit` leaves on the ticket at MR open (superseded by mr-followup when it changes). Each transition looks up `transition_cmd` for the ticket's prefix (`lib/tracker_config.py`, `~/.claude/simo-dev/tracker.json`) and invokes it if configured; not configured (e.g. a read-only tracker) → the step is a no-op, no special-case in any skill body. Never moves the ticket backward. A `transition_cmd` failure — any non-zero exit, including a `--leaf-only` refusal on an **umbrella** (a key with sub-tasks) or a `--sync-parent` exit 7 (the umbrella's sub-tasks are all at/past Done — the close is a user-confirmed gate at post-merge, `simo-dev:mr-followup` step 8.6, or in a release skill mirroring the `next_subtask_cmd` contract) — only prints a warning (or, for intake's rc 8 below, a BLOCKED report); the flow always continues. Intake's `In Progress` call leaves a ticket flagged Blocked on the tracker side untouched (the binding exits 8, and `simo-dev:task-intake` step 5.6 reports it to the user); the post-push and post-merge calls pass `--clear-blocked`, which authorizes the binding to lift such a flag once the work is done. A binding with no Blocked concept accepts and ignores the flag. `--leaf-only` never advances the umbrella key directly; `--sync-parent` (added on every leaf transition) keeps it in sync with the aggregate of its sub-tasks instead — see `simo-dev:task-intake` step 2.5. Set `DEV_FLOW_NO_TRACKER=1` (or drop a `.claude/no-tracker` marker) to skip all transitions for the session.

## Configuring the tracker

Nothing above is JIRA-specific — `lib/tracker_config.py` maps a ticket-key prefix (`CUS`, `ACME`, whatever a project uses) to the commands and settings the flow uses for its tickets, listed below. Config lives at `~/.claude/simo-dev/tracker.json` (global per user, not versioned in this repo; override for tests only via `SIMO_DEV_TRACKER_CONFIG` or `--config`).

```bash
python3 lib/tracker_config.py get <PREFIX> <FIELD>
python3 lib/tracker_config.py set <PREFIX> <FIELD> <VALUE>
python3 lib/tracker_config.py run <PREFIX> <FIELD> [ARGS...]
python3 lib/tracker_config.py ticket-line <KEY>
```

Fields, one per prefix:

- `fetch_skill` — resolves a ticket's title/description/AC/status/links given its key (`task-intake` step 2).
- `transition_cmd` — invoked with the ticket key and a target state to move it forward (see above). It may also receive trailing flags (`--leaf-only`, `--sync-parent`, `--clear-blocked`) and must accept any it has no concept for. Exit code 8 is reserved for "ticket left untouched because it is Blocked on the tracker side" — `task-intake` step 5.6 reports any rc 8 as BLOCKED (see "Ticket auto-transitions" above).
- `create_skill` — creates a new ticket (`task-intake` step 5, `simo-dev:task-intake` step 2.5 for sub-tasks).
- `supports_subtasks` — `true`/`false`; gates automated sub-task creation for cross-repo/team work.
- `post_merge_state` — the state a ticket lands on post-merge; defaults to `Ready for Testing` when unset.
- `post_merge_state_no_deploy` — the state a ticket lands on post-merge instead of `post_merge_state`, when the merged plan's header declares `**Deploy required:** no`; defaults to `Done` when unset for the prefix.
- `next_subtask_cmd` — invoked as `<CMD> <leaf-key> [--resolved-at <state>]` after the post-merge transition; prints one JSON line with the leaf's umbrella, its next ready sibling sub-tasks, the pending ones with a reason, and whether every sub-task is Done. Sole consumer: `simo-dev:mr-followup` step 8.6. Empty stdout (or unconfigured) = no-op.
- `scope_fetch_cmd` — fetches ticket-view text for `lib/jira_scope.py`; `-` means explicitly declined, treated the same as unconfigured.
- `requirements_review_cmd` — writes a drafted Requirements/Acceptance Criteria block back to the ticket; invoked at `task-intake` step 4.5 (ticket mode) or step 5.5 (prompt mode).
- `comment_cmd` — invoked as `<CMD> <key> <body-file>`; posts the file as one ticket comment. Every gate comment the flow posts goes through it (`lib/post_tracker_comment.py`).
- `link_cmd` — invoked as `<CMD> <blocked-key> <blocker-key>`; records a "blocked by" link, already-linked counts as success (`task-intake` step 2.5).
- `assign_cmd` — invoked as `<CMD> <key>`; assigns the ticket to the current user, idempotent (`task-intake` step 5.6).
- `pr_body_ticket_line` — a template, not a command: `{key}` and `{number}` (the digits after the key's last dash) are substituted and the line is appended to the MR/PR body `simo-dev:commit` step 7 generates. Typical value for a tracker backed by the same repo's issues: `Closes #{number}`, so the forge closes the issue on merge. A key not ending in `-<digits>` gets no line. Preview with `ticket-line <KEY>`.
- `browse_url` — a template, not a command: one ticket's web page, with `{key}`, `{number}` and `{repo_url}` (the repo's `origin` as an https web URL) substituted, e.g. `https://tracker.example/browse/{key}` or `{repo_url}/issues/{number}`. The flow reads it only through the dashboard (`lib/flow_dashboard.py`, read-only, also when `simo-dev:mr-followup` step 8.5 regenerates the page), which links each task's ticket but gives no link for a `{repo_url}` template, since it does not know the repo's `origin`; tools outside the flow (a status line) use it to link a branch's ticket. Unconfigured → no link.

An unconfigured field is a silent no-op, never an error — a read-only tracker, or no tracker at all, both work out of the box. To disable tracker integration entirely for a repo or session: `DEV_FLOW_NO_TRACKER=1` or a `.claude/no-tracker` marker file.

Example — wiring `CUS` to an existing `jira-cli` wrapper (illustrative; any command that accepts the same arguments works):

```bash
python3 lib/tracker_config.py set CUS transition_cmd "jira-cli transition"
python3 lib/tracker_config.py set CUS post_merge_state "Ready for Testing"
python3 lib/tracker_config.py set CUS post_merge_state_no_deploy "Done"
```

## Configuring per-repo settings

Settings that belong to a repo rather than to a ticket prefix live in `~/.claude/simo-dev/repo.json` (global per user, not versioned; override for tests only via `SIMO_DEV_REPO_CONFIG` or `--config`), read and written by `lib/repo_config.py`. Entries are keyed by repo-id (`lib/repo_identity.py`): the normalized origin URL (`git.example.com/team/app`), or the main checkout's absolute path when there is no origin — the same value from every worktree of the repo. Not keyed by ticket prefix: one prefix often spans several repos that need different settings.

```bash
python3 lib/repo_config.py get --repo <any-checkout-or-worktree> <FIELD>
python3 lib/repo_config.py set <checkout-path-or-repo-id> <FIELD> <VALUE>
```

`set` accepts a checkout path or a literal repo-id / origin URL, so a repo can be configured without a local clone. Prefer the checkout path; a literal URL must be the one `git remote get-url origin` prints, since an ssh form with a port does not normalize to the same id as its https form. `get` prints the value, or nothing when unset, with rc 0 either way.

Fields, one per repo:

- `release_skill` — a skill name. Sole consumer: `simo-dev:mr-followup` step 8.7, which runs after every other post-merge step and invokes it with the Skill tool and args exactly `post-merge`; the skill owns its own gates and output from there. Unset = no output at all. It needs no ticket, and runs only after a user-confirmed merge. Invocation environment: the task worktree is normally removed by then and the Bash cwd may still point at that unlinked directory, and the main checkout may not have been refreshed. So the skill must not rely on its cwd: it resolves its repo by absolute path and fetches what it needs itself.

Example (illustrative):

```bash
python3 lib/repo_config.py set git.example.com/team/app release_skill my-plugin:my-release
```

## Proactive review-loop auto-run — runtime behavior

Only while the flow is active (see Activation above). When implementation work concludes, the main thread auto-invokes `simo-dev:review-loop` and proceeds — no up-front ask — BEFORE the user asks to commit/push/merge. Catches issues earlier. It skips only when the loop is clearly not useful (trivial doc/typo edit, empty diff, or a review already covering the pending files). Inside a `simo-dev:mr-followup` run nothing the run does is a trigger; any other review-loop waits as "In-scope improvements" (Transparency) and `simo-dev:mr-followup` "No Also-fixed ledger work inside a run" describe. CLAUDE.md carries the eager trigger list — the linguistic phrases, the implementation triggers and the pre-commit/push/merge points — because it is the only surface that carries rule *bodies* on every turn (skill `description` fields are in the listing every turn too, and some do carry an imperative — `simo-dev:commit`'s says never to run `git commit` directly — but a description is budgeted in sentences, not in rule sets). `simo-dev:guide` restates the list for whoever loads that file; neither it nor this one loads by itself. The one mechanical backstop is `hooks/review_loop_warn.py`, self-gated to `git commit` (and, outside the flow, `git push` for the one-line advisory). Two skip conditions are decided by code — "a review already covers the pending files" (`lib/review_marker.py` compares each pending file's mtime against the last review record) and "empty diff" (the hook exits silently on an empty candidate list); "trivial doc/typo edit" is the judgment call. The loop still gates on unresolved findings; a clean run hands off to `simo-dev:commit` directly (step-8 exceptions: standalone review request, headless run, commit pre-flight).

If review-loop runs clean, the next `simo-dev:commit` invocation will default the review-loop gate to skip (per the deterministic `lib/review_marker.py check` in `skills/commit/SKILL.md` step 1), unless step 0.7's harvest writes something, which step 1 then re-reviews. The record lives in `~/.claude/state/review-loop`, written by `hooks/review_record.py` when the code-reviewer subagent *concludes* (`SubagentStop`) — an observed event, not a claim, and deliberately not the `Agent` tool returning, which for a background dispatch is only the launch acknowledgement. The event is necessary and not sufficient: the hook also gates on the reviewer having concluded (a non-empty `last_assistant_message`, or, when the report went out through a `SubagentHandback` call and that field is absent, the transcript ending on that call; an interrupted subagent normally has neither, and one stopped while the handback itself runs already holds its full report), on a line-1 `REPO:` marker naming an existing git repo, and on a session id (read the hook for the full set). There is no TTL: a commit is covered when no file in it is newer than the last review.

## Model strategy

`lib/model_strategy.py` (get/set on `~/.claude/simo-dev/model-strategy.json`, four fixed categories) lets a user pick which model backs each of this plugin's own `Agent` dispatch points, independently of whatever model the session itself is running. `simo-dev:model-strategy` wraps it interactively — easier than the raw CLI shown below.

- Main thread: runs whatever model the session is configured with (e.g. via `/model`) — this plugin does not configure or auto-switch it. The categories below are this plugin's own dispatch points, not the session model.
- `explore_research`: `Explore`'s one dispatch site (`task-intake` step 3) reads `lib/model_strategy.py get explore_research`, defaulting to `sonnet` when unconfigured (today's behavior, unchanged) — no longer a hardcoded pin at that call site.
- `code_review`: `simo-dev:code-reviewer`'s three dispatch sites (`code-review-protocol`, `mr-followup` local review, `mr-review` step 5) each read `lib/model_strategy.py get code_review` before dispatch and pass `model:` only when non-empty — still no `model:` pin in `agents/code-reviewer.md` itself; an empty config reproduces today's inherit-the-caller's-tier behavior. Effort is a different lever: the `Agent` tool takes no per-dispatch effort, so `model_strategy` covers model only, and both reviewer agents (`code-reviewer`, `plan-reviewer`) pin `effort: high` in their own frontmatter and deny `Edit`/`Write`/`NotebookEdit` via `disallowedTools` (Bash stays). Two known limits of the pin: per the subagent docs it overrides the session's effort, so it would also lower a reviewer under an `xhigh`/`max` session (per docs, not measured); and its behavior when `model_strategy` points a reviewer at a model without effort support (e.g. Haiku 4.5) is untested. `Plan` (the built-in agent) has no dispatch site in this plugin, so it is unaffected and keeps inheriting the caller's tier with no config hook.
- `plan_critique` (at most one round, and only with a `risk:` line, on a decided brief — "Decided brief" below; skipped entirely for a bare plan — same condition as the **Plan review gate** exception above: step 4c's `Choices made:` list came back empty, so no writer runs): task-intake step 7.5's critique rounds dispatch a new `simo-dev:plan-reviewer` agent on the writer's plan (and on the fast-path round), passing the plan and brief paths, never their content, reading `lib/model_strategy.py get plan_critique` and defaulting to `sonnet` when unconfigured — a call-site default, same pattern as `explore_research`. Set it to `none` to disable automatic plan critique dispatch entirely. `plan-reviewer` carries the same `effort: high` pin and read-only tool denial as `code-reviewer` (see the `code_review` bullet, limits included).
- `plan_execute`: `simo-dev:plan-execute`'s own execution delegation gate (step 1, decided and announced, not asked) reads the `model:` line of `lib/plan_execute_preflight.py` (from `lib/model_strategy.py get plan_execute`) before its executor or per-task/per-batch `Agent` dispatch (`simo-dev:review-loop`'s fixer subagent uses the same value) and passes `model:` only when non-empty — same inherit-the-caller's-tier default as `code_review`, no `none` sentinel (that concept is `plan_critique`-specific). The executor is `simo-dev:plan-executor` (`agents/plan-executor.md`: no model pin, no `Agent` tool, `experimental: { cacheTtl: 1h }`), because its build and test runs often outlast the subagents' default 5-minute prompt cache and each such pause rewrote its whole context; the field loses to, among others (read in the 2.1.326 binary, not a closed list), `FORCE_PROMPT_CACHING_5M`, the `subagentPromptCacheTtl` setting and `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`, and `1h` is ignored while a subscription is in overage. The per-task dispatches and the fixer stay on the default `subagent_type`: they rarely pause that long, and a 1-hour cache write costs more than a 5-minute one. With `plan_execute` empty, any of these runs on whatever model the agent type resolves to — a user-level `general-purpose` override pinning a model applies to the default-type dispatches, not to `plan-executor`.
- No category for the plan writer: `simo-dev:plan-writer` (`agents/plan-writer.md`: no model pin, no `Agent` tool, `experimental: { cacheTtl: 1h }`, since it waits on `plan-reviewer` rounds and on the user at the plan gate) inherits the session's model — plan quality sets execution quality. `task-intake` step 7 dispatches it with a brief file and resumes it with `SendMessage` for every critique fix and gate edit.
- Background `Agent` calls (not `Bash`) doing mechanical work (log tail, doc generation, wide read-only scans) are not wired to any category above, and no script in this plugin dispatches one today — treat that as a documented intention for a future dispatch, not enforced behavior.
- Every subagent this plugin dispatches (`Explore`, `code-reviewer`, `plan-reviewer`, or any other `Agent`-tool child) must work in-line within its own turn and return its findings as its final message — never spawning its own `Agent` children, never using `run_in_background`. A subagent can't await its own background children, so the dispatching skill would get an empty punt instead of the results. It also inherits the caller's Scratchpad directory in its environment block, so a throwaway script it writes there can overwrite a same-named one of the caller's: `code-reviewer`/`plan-reviewer` carry a `mktemp -d` rule in their own definition, and the dispatch prompts of `task-intake` (step 3 `Explore`, step 7 `plan-writer`), `plan-execute` (delegated tasks and the executor), `review-loop` (the fixer), `commit` step 7 and `mr-review` (the `mr_presentation` agent, line appended at dispatch) carry it as a line. A new dispatch site needs the same line, and so does a reviewer dispatch overridden to a non-simo-dev agent type (e.g. `mr-review`'s `DEV_REVIEW_MR_AGENT_TYPE`), which loses the definition's rule. The `/tmp/claude_` prefix keeps the dir inside the usual `/tmp/claude_*` allow rules; a bare `mktemp -d` lands under `$TMPDIR`.

Example — opting `code_review` into a higher-tier model (illustrative; the config file does not exist until the first `set`, so nothing here changes behavior by default):

```bash
python3 lib/model_strategy.py set code_review opus
```

## Dev-flow journal & knowledge harvest

Each task is recorded as a stream of **flow events** (`lib/flow_telemetry.py`) in `~/.claude/state/dev-flow/<task-id>.jsonl`. `task-intake` step 1 mints the task ID (`<YYYYMMDDTHHMM>-<session8>`) and keeps it in the flow flag; a hand-off `start_session` child of the same task inherits it (its prompt's `task id:` line). Events: `step_start` (the Skill hook `hooks/skill_logger.py`, plus `task-intake` itself), `task_bound` (ticket, branch, repo — step 6), `gate` (direction and plan gates, the direction gate recording `brief` on a decided brief; `intake_path` (`fast`, `fallback`, `full` or `resume`, "Decided brief" below; a resume also records `resume_point` with its entry), review-loop and mr-followup exits, MR creation, and `handoff=released` when `close` ends a session's share of the task), `retry` (review-loop iterations and mr-followup rounds from the second on), `outcome` and `attribution` (step 8.5), and `task_link` (`parent`: the task whose session started this one, written by `start --parent-task`). An event holds names, short answers, counts and times — never prompts, code or diffs; `outcome` alone carries three short summaries (task, friction, notes). Outside a task only `step_start` of `simo-dev:*` skills is kept, in `session-<session-id>.jsonl`, until a session that never took part in a task runs a work step of the flow (`plan-write`, `plan-execute`, `review-loop`, `commit`, `mr-followup`: `ADOPT_SKILLS`) — typically a session another one started, which goes straight to `simo-dev:commit` without `task-intake`. Then the Skill hook calls `flow_telemetry.adopt` and the session gets an **adopted task**: its ID is the `task id:` line of the session's first prompt (a hand-off child joins its task, unless that task already has an `outcome`, which then becomes the parent when no `parent task:` line names one) or a new one; the prompt's `parent task:` line becomes its `task_link`; a `gate` `adopted`=`no-intake` dated at the transcript's first record opens its window, so the work done before that step counts in the task (in a new task, under its moved earlier steps or the `(none)` row); and the session's `session-*.jsonl` lines move into the task file. The adopted ID lives in `~/.claude/state/dev-flow/adopted/<session-id>`: `current` reads it, `flow_state.py is-active` does not, so adoption leaves the flow state as it was (a session without the flag gets no eager review-loop, no reminders). Step 8.5 records and `close`s it like any task; a later `task-intake` in that session releases it (a `handoff` gate) and starts its own task. A session whose task was closed is not adopted again: what it runs afterwards stays in `session-<session-id>.jsonl`.

After each merged task, `simo-dev:mr-followup` step 8.5 records the `outcome`, and writing that event (`flow_telemetry.py event --type outcome`, from step 8.5 or by hand) attributes the task's tokens after the fact from its sessions' transcripts (main thread plus `subagents/agent-*.jsonl`; four categories — input, cache creation, cache read, output — deduped by `message.id`, inside the task's time window; `lib/transcript_usage.py`) per step, each record also priced at its own model's list price (`cost`, rules under **Tokens per step** below), regenerates `~/.claude/state/dev-flow-journal.md` whole from every task file (`flow_telemetry.py render`; step durations follow the step model below), and clears the session's task ID. A merge typed by hand (`glab mr merge`, `glab api …/merge`, `gh pr merge`) never reaches step 8.5, so the Bash hook `hooks/mr_followup_remind.py` reminds to run it when the session still holds a task with no `outcome`. The journal is a view: edit the events, never the file. The hand-written journal from before flow events was moved once to `dev-flow-journal-archive.md` next to it. Session and unfinished task files untouched for 90 days are pruned; finished tasks stay. `lib/session_tokens.py` sums one session the same way, as a standalone CLI. No A/B experiment framing — this is a personal operational log.

**Parent task.** A session that starts a *different* task with `start_session` (a follow-up, the next sub-task) puts the line `parent task: <id>` in the spawned prompt, `<id>` being what `flow_telemetry.py current --session "$CLAUDE_CODE_SESSION_ID" --cwd "<worktree-abs>"` prints (no line when it prints nothing). After `simo-dev:mr-followup` step 8.5 the flow stays on but `close` has cleared the session's task, so `current` prints nothing: a follow-up started after the merge takes the `TASK=` value step 8.5 printed instead. `task-intake` step 1 passes it to `start` as `--parent-task`, which records a `task_link` event (a child that skips intake gets the same event from `adopt`, which reads the line from the transcript); a value that is not a well-formed task ID, or is this task's own ID, is ignored with a warning and the task still starts; a well-formed ID of an unknown task is kept, and the dashboard shows that follow-up as a root. It is not the hand-off `task id:` line: that one keeps the same task in a new session, this one names an earlier task. The journal shows it as a `parent task` line.

**Decided brief.** A session started with scope, files and acceptance criteria already decided does not need the full intake. The starting side says so explicitly, with this block in the brief:

```
direction: decided
decisions:
- <one decision taken>
risk: <one line>
```

At least one `- <decision>` line is required; `risk:` is optional. `simo-dev:spawn-task` writes it, together with a `simo-dev:task-intake` invocation line, when the flow is active and a follow-up's direction is decided; a hand-written brief can carry it too. `task-intake` step 1 reads it from its own arguments, or from the spawned prompt for the first intake of the session, and never infers it from prose. On a hit it follows `skills/task-intake/lib/fast-path.md`: a quick check of the brief against the code replaces the Explore analysis, there is no direction gate, the plan is short (files, steps, checks, no full code) and written without `plan-write`, and `plan-reviewer` runs at most one round, only when the brief has a `risk:` line. The plan review gate, review-loop, the tests and the merge gate are unchanged. A contradiction found by the check (a missing file, a false claim, a path to create that already exists), or `restart` at the plan gate, falls back to the full flow and says why. Every intake records its path as `intake_path` (`fast`, `fallback`, `full`, or `resume` for the resume check of step 1), so the dashboard can tell the paths apart (column, and group headers with task count and summed cost; per-task cost and duration are in the rows); tasks from before this change show `—`. A hand-off child (`lib/handoff-spawn.md`) skips intake and carries no block: its prompt and every `plan-execute` dispatch state what the session or agent owns instead of listing edits.

**Tokens per step.** One step model, `lib/flow_telemetry.py` `step_marks` and `split_by_step`, used by `attribute`, by the dashboard and by the journal's `steps:` line. Per session, a step opens at each `step_start` of a flow step (`STEP_SKILLS`: `task-intake`, `grill-me`, `plan-write`, `plan-execute`, `review-loop`, `commit`, `mr-followup`), and at a `retry` of a flow step other than the one open there (the flow went back to it: a resume). Any other skill (`code-review-protocol`, a project skill run during `plan-execute`) is a helper: its `step_start` event is kept, and its cost stays on the step that called it; it opens a step only when the session has none yet. The Skill hook only signals that a skill started, never that it ended, so one `gate` opens a step: a `review-loop` opened while `commit` was the open step is `commit`'s pre-flight, and its `review_exit` gate reopens `commit`, which then holds the push and the MR. A row's tokens and cost already include its subagents; the per-agent figures break that sum down. A main-thread usage record goes to the step open in its session at its own time; a subagent's transcript, as far as it falls inside the task's window, goes to the step open at its launch (its first usage record), even when it is resumed later (one launched before any step goes by each record's own time), labelled with the `agentType` of its `agent-*.meta.json`. A record before its own session's first step (a hand-off child's first turn) goes to the step open at that time in any session (the latest started before it), so `(none)` holds only what precedes the task's first step. The `attribution` event stores the result as `by_step` (one row per step: skill, session, start, the four categories, and the same per subagent type), and its rows sum to `total`. Task files written before this carry `by_skill`, grouped by the transcript's own skill label, which was empty for most records; the dashboard still reads it. With `--session` and no task there are no step events, so `attribute` prints only its summary line. The two readers share the step model, not the record window: `attribute` counts each session from the task's first event, the dashboard from that session's first event of the task (its owned spans), so on a hand-off the event can hold a hand-off child's first turn that the live page leaves out. The cost has one definition, `lib/transcript_usage.py` `PRICES`: list prices in USD per million tokens from the official Anthropic pricing page, with the date they were checked. Each usage record is priced at its own `message.model` (a `[1m]` tag or a date suffix stripped), its 1-hour cache writes (`usage.cache_creation.ephemeral_1h_input_tokens`) at the 1h rate and the rest at the 5-minute rate, and a model with a long-prompt tier (Haiku 5.5, over 100,000 prompt tokens counting cache reads and writes) at that tier per request. Every `by_step` row carries `cost` (USD per category) and `agent_costs`, and the event carries `cost` and `unpriced`. A model with no `PRICES` entry, or a record with no model, is priced as `FALLBACK_MODEL` (`claude-opus-5-5`), and a record whose `usage.speed` is not standard (fast mode) at standard rates: never silently, it goes in `unpriced` (`<model>` or `<model> (fast)`) and the note counts it, and the journal and the dashboard mark the figure `≈`. Server-tool charges (web search) are not included. An event written before costs has no model data: the journal and the dashboard price its tokens at `FALLBACK_MODEL` and 5-minute writes, marked `≈`. `attribute` prints the cost on its summary line (`cost=$…`), the journal's tokens line and the dashboard use it; all of them are estimates at list price, not a bill. A total quoted by hand in an `outcome` field is not one: `notes` carries no token totals.

**Dashboard.** `python3 lib/flow_dashboard.py [--out PATH] [--task TASK_ID] [--no-reconcile]` writes one self-contained HTML page (inline CSS and SVG, nothing loaded from the network) to `~/.claude/state/dev-flow-dashboard.html`, or to `$SIMO_DEV_DASHBOARD` when set. `simo-dev:mr-followup` step 8.5 regenerates it after each merged task, right after the journal; run it by hand, or on a timer of your own, to see tasks still in progress. It runs locally. Before a full build (not with `--task`, nor `--no-reconcile`) it runs `flow_telemetry.py reconcile`: a task with an `mr_created` gate and no `outcome` whose MR/PR (the `pr-link` record of the gate's session transcript nearest to that gate, within 10 minutes) was merged at least 2 hours earlier from the task's branch (`glab api`, `gh pr view`, github.com only; each open task at most once every 15 minutes, remembered in `reconcile-checked.json` next to the task files, with a `.lock` that makes a concurrent run skip) gets an `outcome` with result `merged`, dated at the merge, and the journal is re-rendered; so a task merged from the forge UI, by a batch session or after its session was archived stops showing as `stale`. A closed MR/PR, or a task with no such record, stays open. The 2 hours let a live post-merge step record the merge first, but are no guarantee: a step 8.5 run later still adds its own `outcome`, and the latest one wins. Those are its only writes besides the page and its cache. The transcripts are never written; its one other file is a parse cache, `~/.claude/state/dev-flow-dashboard-cache.json` (`$SIMO_DEV_DASHBOARD_CACHE`), keyed by the size and mtime of every transcript file a session's parse reads and holding no message text (a timestamp and a kind per record, the usage records, the subagent spans, the session title), so a finished task is parsed once and a later run re-reads only the sessions that changed; a session whose transcript Claude Code has since pruned is served from its cache entry, and a run where nothing changed leaves the file untouched. Each cached usage record keeps its model and its 1-hour cache-write share, for pricing. A change of the cache format (`CACHE_VERSION`) drops every entry, those of already-pruned transcripts included: a task whose sessions were all pruned falls back to its `attribution` event, one with a session still on disk shows only that session's tokens. The page is split into views, one tab each once its script runs (without it they follow one another): **Overview** (the summary cards and the cost by step) and **Tasks** (the task table and the task sections); a link to a task, or a URL ending in `#task-<id>`, opens the Tasks tab on it, and the auto-refresh keeps the tab. The Overview opens with summary cards (tasks and how many merged, how many running and stale, mean and median estimated cost of the tasks with tokens, total cache read, cache share of input, total human wait; then, when there are untracked runs, their total estimated cost), and a **cost by step** table (`step_totals`): every step of every task on the page summed by skill, costliest first, with its runs, the tasks it ran in, the estimated cost (a bar on the same categories), its share of all task cost, the cost per run, the wall time (human waits included), the part spent by subagents launched in it, and the cache %; the tokens before a task's first step are their own row, a task whose attribution event has only the old per-skill table is counted in the share and named in a note, and the task-table filters do not apply. Then an overview row per task, sized to fit the page width (name, repo and branch wrap; on a narrow screen the table still scrolls): its name, status, start, repo and branch, ticket, MR (`MR !N` or `PR #N` when the URL ends in a number), duration, estimated cost (`$ est.`, with a bar stacked by the cost of each token category, one scale for every row: the costliest task's cost; a session row gets a thinner bar on that scale), cache %, review-loop/mr-followup rounds, human wait and intake path (`fast`/`fallback`/`full`, `—` when not recorded; the overview also groups by it, with per-group totals). **Status** comes from the task file alone, at generation time (the page header shows that time): `done` when the task has an `outcome`, shown as its `result` (`merged` is what `mr-followup`'s post-merge step writes; any other value gets a red badge); else `running` when its last activity is at most `STALE_AFTER_H` (24h) old, `stale` past that or with no timed event. An open task's last activity is its last event or the last transcript record of its sessions inside its owned spans (below), so a long step with no event stays running while its session works; 24h lets a task paused overnight stay running and flags one untouched for a full day. The `active/` flags of `lib/flow_state.py` are not used: they mark a session's flow on, not a task's state, and are not cleared at merge. Rows are ordered running first, then stale, then done, newest first inside each. A small inline script sorts the rows by any column, filters them by text, by status and by period (last activity in the last 7, 30 or 90 days before the page was generated), shows them 25 tasks per page with the count, cost and cache % of the rows that pass the filters, and groups them by status, by repo, by session or by task tree, with a total per group (over all its filtered rows, not only the page's); a task's section shows only while its row is on the page; the page is complete without the script, the session rows then shown under each task. An auto-refresh select at the top (off, every 1, 5 or 15 minutes; 5 unless the viewer picked another, kept in the browser's `localStorage`) reloads the page while it is visible, never while a filter is being typed, and keeps the filters, period, grouping, sort, page, scroll and open sections across the reload (`sessionStorage`, read once). It only reloads the file, so the data is as fresh as the last generation: pair it with a timer of your own that runs `flow_dashboard.py` (a launchd agent every 15 minutes, say); with the cache a run that changed nothing takes well under a second. In the session grouping a task's first session is its group, and each task's sessions are nested under it in the order they joined, with their own estimated cost and cache %, summing to the task total (a task on the attribution fallback shows zero on its session rows). In the task-tree grouping each tree is a group: follow-up tasks sit under the task that started them, indented by depth, in tree order inside the group (a column sort then orders the groups only); a task alone in its tree gets no group header, and a parent that is no known task leaves the follow-up a root. Each task section names its parent task and its follow-ups, linked to their sections when they are in the page (with `--task`, the others show as plain IDs). Per task a collapsible section, in the same status order with the first one open, shows the status badge and the MR link in its header and holds a timeline with four lanes (steps, subagents, human waits, gates and retries) and a legend, the subagents (type, description, duration) and gates listed in clear, a `≈` note naming any model priced as `FALLBACK_MODEL` (or saying the attribution event has no model data), and a table of tokens per step: step number, the four categories plus the estimated cost and cache %, the costliest step highlighted, each subagent type listed under the step it was launched in, and a "before the first step" row when that is not zero. Cache % is cache read / (input + cache write + cache read). The task name is the last `custom-title` record of the session that joined the task last (on a hand-off, the child session that implements and opens the MR), else of an earlier session, else the branch; that record has no timestamp, so a session that hosted several tasks gives each its latest title. The ticket links through the tracker config's `browse_url`, read-only; a `{repo_url}` template gives no link here. What no event records is derived from the transcripts when the page is built: the steps are those of **Tokens per step** above, so a nested helper skill (tdd, verify-done, …) opens no step and its tokens stay on its caller, and a step ends at the next step's start in any session; the last step ends at the outcome, or at the session's last activity. The journal's step durations use the same step model, each step ending at the next one's start. When sessions are shared, each task owns, per session, the time from each of its events to the next event of another task in that session, or to its own handoff gate; a later event of the task reopens it. Tokens, subagents and waits are kept only inside those spans (a wait is never bridged across another task), and a closed task's session also stops at its own last event, as `attribute` does. Subagents come from `subagents/agent-*.jsonl` and the `.meta.json` next to each. Human waits are an estimate: a gap over 60s between the last main-thread reply and the next real user turn, skipping tool results (except the answer to an `AskUserQuestion`, a gate), background-task and side-session notifications, compaction summaries and app-injected turns (`turnOrigin` other than human); overlapping waits of two sessions count once. The page is written with mode 0600, like the event files. Tokens per step are the transcript usage records (deduped by `message.id`) split by the same step model; with no transcript usage at all the page falls back to the last `attribution` event: its `by_step`, else the old `by_skill` table. Every session with `session-*.jsonl` lines, minus the `task-intake` line written seconds before `start` mints the task, is an **untracked run** (`untracked_runs`): a row of the task table and a section like a task's, status `untracked` (after done in the order, a filter value of its own), its steps those of the same step model over the session's `step_start` events (the first skill of the session opens a step even when it is not a flow step), its tokens those outside every task's spans (`free_spans`, the complement of `task_spans`) split by the same step model, so its steps count in the cost by step; the summary cards about tasks leave it out, the Tasks tab counts it apart (`N + M untracked`) and `--task` shows none. These runs are simo-dev skills with no task ID. Cases seen: a session that ran no work step (an adopted session's earlier lines move into its task, see **adopted task** above); a session that ran simo-dev skills after its task was closed (never adopted again); a session from before adoption existed, e.g. one started by another (`start_session`) that went straight to `commit` without `task-intake`; one from before task IDs. A session that never ran a simo-dev skill writes no `session-*.jsonl` line (the Skill hook skips other skills) and is not shown; a run whose transcript is gone and not cached has no tokens. "Pipeline 1st" is not recorded yet: the page header says so, and the mr-followup rounds are the proxy.

**Step replay.** To judge a flow change before adopting it, `lib/step_replay.py` replays one step (today `plan-write` with its critique) on a frozen input, N times per plugin variant, each run in an isolated snapshot and sandbox, and compares cost and outcome against the noise measured between runs of the same variant: `docs/step-replay.md`.

Known gaps, proposals not implemented:
- No event records the pipeline status, so "pipeline 1st" cannot be computed; a `gate` with the first round's pipeline result in `simo-dev:mr-followup` would fill it.
- The Skill hook fires before `task-intake` runs `start`, so every intake also leaves a `step_start` in `session-<id>.jsonl`; the dashboard drops it, `skill_logger.py` could skip it instead.
- A task links to its parent only when the spawning prompt carried the `parent task:` line (read by `task-intake` step 1, or by `adopt` when the child skips intake); otherwise the follow-up is a root: a follow-up started by hand, before the link existed, by a `start_session` call that goes through neither `simo-dev:spawn-task` nor one of the flow's own spawn points, or after the merge once step 8.5's `TASK=` line is no longer in the session's context (e.g. after a compaction).
- No `step_end`: the last step of a task ends at its outcome or last activity, and human waits are estimated from transcript gaps, not recorded. A tool-permission prompt leaves no trace in the transcript, so the time spent on it is not counted as a wait.

domain terms → `CONTEXT.md`, hard-to-reverse decisions → `docs/adr/`, gotchas/invariants →
`CLAUDE.md` or a reference file — runs pre-merge, not here. `commit` step 0.7 runs the primary,
full pass before every commit, ahead of its review pre-flight; `mr-followup` step 7's clean-exit
branch runs a lighter catch-up pass scoped to what emerged since `commit` step 0.7 (a step-1

## In-scope improvements

An **In-scope improvement** is a change beyond the literal request that touches only files already in the current task's diff or plan.

- **Never spawn a follow-up for one** (`start_session` or otherwise): do it in the current task.
- Needs the user's decision (a reasonable alternative exists) or would swell the diff noticeably → ask in-session. Never spawn silently, never skip silently.
- A change reaching any file or repo outside the task stays a follow-up (existing spawn rules unchanged).
- **Pre-existing dead code** in a file in the diff: delete it when `rg -uu` over the repo finds no other use of the symbol (hits only in plans/specs under `docs/` or in build output are not uses — name them in the evidence); the evidence goes in the "Also fixed" entry. Not verifiable by search (reflection, runtime-built names, external entry points) → ask. Outside the diff → mention only.
- **Review findings**: `low` findings on files in the diff are applied while an iteration remains under `CAP`. This can cost up to the iterations remaining under `CAP` (each review may surface new `low`s), never more. On the last iteration they are listed only: editing after a clean exit invalidates the review record. An applied `low` is an In-scope improvement only when the **branch-point check** says so: `lib/branch_point_check.py`, run once per iteration/round, before any fix of it is applied, on every `low` that passed the validity filter, against the merge-base the calling skill's review diff used. Its targets are the cited `file:line` plus every line the fix will replace or remove, or, for a fix that only inserts, the lines on both sides of the insertion point. All `pre-existing` → In-scope improvement. Any `branch-added` → a fix of the branch's own work, which is part of the requested work, not beyond it: applied, not ledgered, not under "Also fixed". `error`, or no verdict (the call failed) → same as `branch-added`, and named in the skill's report. A `low` from a remote MR comment, or a `low`, `simo-dev:plan-execute` improvement or ad-hoc edit that completes the branch's own change (e.g. documents a flag the branch added, on a pre-existing line, or re-adds a line the branch removed), is never an In-scope improvement, whatever the check says.
- **Unattended runs never ask**: one needing a decision is skipped and reported as `deferred (needs decision)`.
- **Transparency**: each one is declared in one line (file, what, why) — in the commit message body of the first commit that carries it, and in the MR body's `### Also fixed` section when the MR is created. Once the MR exists (mr-followup rounds, later commits) the commit message is the record; the MR body is not rewritten. One known at plan time also gets its own plan task. Every one made through `simo-dev:commit` (plan-execute, review-loop, an ad-hoc edit in the flow; for review-loop an applied `low` only on an all-`pre-existing` branch-point check; for plan-execute or an ad-hoc edit, any improvement but the one a task titled `In-scope improvement — …` is named after (a plan-execute-only exemption) only on an all-`pre-existing` branch-point check run before the edit, whose targets are the lines the improvement will replace or remove, or both sides of a pure insertion, the first line alone at start of file and the last line alone at end of file, since neither, unlike a review finding, has a cited `file:line`) is recorded in the **Also-fixed ledger** as soon as it is made: `lib/also_fixed_ledger.py add`, always in the single call form of `skills/review-loop/lib/fixer-steps.md` "6. Auto-apply fixes" (copy that `add` block for an ad-hoc edit, after the check in the sub-bullet below) — absolute `--repo`, one single-quoted `file — what — why` argument per improvement, `file` relative to the repo root exactly as `git status --porcelain` prints it (any other path form is later dropped as stale); a reverted one is removed with `drop`, same form; skipped on a protected branch. ## Code review severity

Used by `simo-dev:review-loop` and `simo-dev:mr-followup`.

- `low` — style/cosmetic. On a file in the diff, applied per "In-scope improvements" (under `CAP`); otherwise informational.
- `medium` — code smell, missing test coverage, minor bug, perf concern. Auto-fixed.
- `high` — correctness bug, security issue, data-loss risk. Auto-fixed.
- `critical` — blocks merge. Auto-fixed; surfaced even if iteration cap is reached.

Reviewer subagent must emit findings as `[severity] file:line — message` (one per line).

## Deferred-tool availability

A tool can be callable, listed only as deferred, or absent in a given session. Every availability gate on a tool that can be deferred decides the same way:

- Already callable (including loaded earlier this session) → use it.
- Otherwise (listed only as deferred, or not listed at all) → run `ToolSearch` `select:<full-tool-name>` once. Never skip that load because the name is not listed.
- Schema returned → available. No schema (a denied or failed `ToolSearch` included), or no `ToolSearch` tool → not available: the site's own fallback, unchanged.

Tools gated this way (observed, not a closed set): `SendMessage`, `mcp__ccd_session__start_session`, `mcp__ccd_session__mark_chapter`, `mcp__visualize__show_widget`, the `mcp__ccd_session_mgmt__*` tools. Each site states the load inline and keeps its own fallback; none depends on this section being read.

Observed 2026-09-30: the visualize server can register only under a hashed `mcp__<uuid>__` prefix. `select:` on the canonical name then returns no schema and the site falls back — expected, not a regression.

## Local dev refresh

The `simo-local` marketplace is a directory source: the installed copy is cached at `~/.claude/plugins/cache/simo-local/simo-dev/<version>/` and `claude plugin update` is a **no-op unless `plugin.json` `version` is bumped**. After editing the plugin source in place, force a fresh cache with:

```bash
claude plugin uninstall simo-dev@simo-local && claude plugin install simo-dev@simo-local
```

(or bump `version` in `plugin.json`). Restart Claude Code / `/reload-plugins` to load the refreshed skills.
